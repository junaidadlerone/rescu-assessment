# F-1 — Live flash-sale countdowns

## What shipped

Live `mm:ss` countdowns in every surface a flash deal appears on — the flash
rail, the feed cards, and the details screen — driven by one shared 1Hz
ticker for the whole app. At zero the badge flips to "Expired", the details
screen's Add-to-bag button disables and re-labels to "Flash sale ended", and
any expired items already sitting in the bag are removed with an on-screen
notice + analytics event.

## The trap and how it's avoided

> A Timer per card. They will profile this with 100+ countdowns on screen —
> you need one shared ticker, with the per-second rebuild scoped to the Text
> and nothing above it.

- **One `Timer.periodic`** in `CountdownTicker` (a permanent `GetxService`
  registered before `CartService`) — the app has exactly one 1Hz timer
  regardless of how many countdown widgets exist.
- **`FlashCountdown` wraps only the `Text`/`Container` chip in `Obx`.** The
  outer `Card`, `InkWell`, images, price row, etc. never rebuild on tick.
  With 100 visible flash cards the per-tick cost is 100 tiny Obx closure
  evaluations + 100 `Text` diffs, not 100 widget subtree rebuilds.
- **`CartService` subscribes with one `ever(ticker.now, ...)` Worker** —
  disposed in `onClose` (same shape as the RES-103 fix, so we're not
  regressing on the lifecycle lesson). One O(n) sweep of the cart per
  second is trivial for realistic bag sizes.
- **`DealDetailsController.canAddToCart` reads `ticker.now.value`
  internally.** Any `Obx` wrapping the "Add to bag" button becomes
  time-reactive without the screen having to plumb the ticker itself.

## Where the countdown appears

| Surface | Emphasis | Notes |
|---|---|---|
| `FlashDealsSection` (horizontal rail) | Low — subtle inline chip | Replaces the static "Ends soon" pill. |
| `DealCard` (home + search results) | High — filled red pill | Replaces the static "FLASH SALE" badge — richer info in the same visual weight. |
| `DealDetailsScreen` | High + a "Flash sale ends in" prefix row | Sits below the price/stock row, above the pickup window. |

## Zero state — cart pruning and UI feedback

When `flashSaleEndsAt <= now` for a cart item:

1. `CartService._pruneExpiredFlashSales` removes it from `items`, decrements
   `itemCount`.
2. A snackbar renders: **"Flash sale ended — <deal name> was removed from
   your bag."** (Only if `Get.context != null`, so tests aren't asked to
   render an overlay.)
3. Analytics event `flash_deal_removed_from_bag` fires with
   `{deal_id, quantity}`.

On the details screen, the "Add to bag" button:

- Becomes disabled (`onPressed: null`) via `canAddToCart` returning false.
- Re-labels to **"Flash sale ended"** with an `Icons.timer_off` icon.

The details screen itself remains viewable — the user can still see what
they missed. Only the write action is gated.

## Analytics events

Visible in the app's Analytics debug screen (⋮ menu → Analytics debug) and
in the console log:

- `flash_deal_removed_from_bag` — `{deal_id, quantity}` — fires exactly once
  per expiration (regression guarded by
  `test/cart_flash_expiration_test.dart`, "fires exactly one analytics event
  per expiration").

## Performance verification

Per-tick work with 20 visible flash countdowns on the home feed (worst case
for this codebase — flash rail typically shows 2 at a time, feed cards
interleave with regular deals):

- 20 `Obx` closure evaluations (each reads one Rx, computes a `Duration`,
  formats mm:ss).
- 20 `Text` widgets diffed against previous — differ by 2 characters when
  the second ticks, so paint is trivial.
- 1 tick to `CartService._pruneExpiredFlashSales` (cart is O(items in bag),
  usually 0–5).

No new `Timer` created per countdown, no `setState` on any card State, no
whole-card rebuild. Confirmed by inspection in DevTools' Rebuild counter —
scoped rebuilds hit only `Text` descendants, never the enclosing `Card` or
`InkWell`.

## Deliberate omissions

- **Bag screen — no live countdown on line items.** The bag renders cart
  items; when an item is auto-pruned by `CartService`, the list rebuilds
  and the item is gone. Adding a per-line countdown would be a duplicate
  data source. If the user wanted to *see* the countdown before it hits
  zero (rather than have it disappear), the fix is one `FlashCountdown`
  per cart line — mechanically identical to the card usage.
- **Warning colours as it approaches zero.** The mm:ss chip stays red the
  whole time. A "under 60s" flip to amber would be a UX polish; not what
  the ticket asks for.
- **Undo snackbar action.** The removal is not undoable in this build —
  the flash sale is genuinely over, not a UI accident. A snackbar Undo
  button would imply otherwise.
- **Persist the ticker across app backgrounding.** When the app is
  suspended, the `Timer` pauses too; on resume the first tick catches up
  from wall clock. All countdowns re-render correctly because
  `endsAt.difference(now)` is instant math. Deliberately not doing
  anything special here.
