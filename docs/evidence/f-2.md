# F-2 — Impression tracking

## What shipped

`deal_impression` fires when a card is ≥50% visible for 1 continuous second,
once per deal per session across every surface it appears on. Events are
batched and flushed to `FakeApiService.sendAnalyticsBatch` at the earlier
of 10 pending events or 15 seconds since the first unsent event.

Verified on **Home → ⋮ → Analytics debug**.

## Design in two moving parts

Split cleanly along the dwell / dedup / batch axes:

### 1. `ImpressionTracked` — the per-card widget

Wraps its child in a `VisibilityDetector` and owns a **per-instance** dwell
`Timer(dwell)`. Fires the timer when visibility crosses ≥50%; cancels it
when visibility drops below 50%. The trap the ticket warns about — "scrolling
straight past a card must not count" — falls out of this naturally: a card
that appears and disappears in 400ms cancels its own timer before it fires.

`VisibilityKey` is `impression-<dealId>-<source>` — unique across surfaces
so the same deal on both home and search doesn't collide the detector's
per-key state.

**Not doing:** debouncing visibility notifications ourselves. The package
already coalesces `~500ms` of change notifications into a single callback.
That's why per-card overhead is small even in a fast scroll: the callback
fires once per visibility change, not per scroll frame.

### 2. `ImpressionTracker` — the session-and-batch service

- **Session dedup** via `Set<int> _seen`. `recordImpression` early-returns
  if the deal is already logged this session, regardless of which surface's
  widget called it. Two widgets watching the same deal both call in; the
  second is dropped.
- **Local sink** via `AnalyticsService.logEvent` — the on-device Analytics
  debug screen shows events immediately, without waiting for the batch
  flush. Critical for verification and for the "Verified on Analytics
  debug" requirement in the ticket.
- **Batch flush** — the ticket's exact rule:
  - 10 events pending → immediate flush.
  - Otherwise a Timer armed on the first-in-batch fires at 15s.
  - The 15s clock is anchored on the **first** unsent event, not reset on
    each add. Regression-guarded in the test suite ("the 15s clock is
    anchored on the FIRST unsent event, not the last").
- Backend failures don't crash the app. `LogService.error` logs it; the
  local sink already captured the events for the debug screen.

## Surfaces wired

Every place that renders a `DealCard` or an equivalent card in a list gets
wrapped:

| Surface | Source string | Position |
|---|---|---|
| `HomeScreen` sliver list | `'home'` | Index in the filtered `visibleDeals` list |
| `SearchScreen` result list | `'search'` | Index in `results` |
| `FlashDealsSection` horizontal rail | `'flash_rail'` | Index in `deals` |

**Not wired:**

- **`DealDetailsScreen`.** Viewing a detail page already fires the more
  specific `deal_details_view` event. Adding a `deal_impression` on top
  would double-count without adding information.
- **`CartScreen`.** Items in the bag are already an active choice — "seeing
  the bag" isn't an impression signal.
- **`MapScreen`.** Deals surface as map pins with different visibility
  semantics (a pin is either visible or not — no 50% partial). Would need
  its own tracking design.

## Analytics events

Visible on **Home → ⋮ → Analytics debug**:

- `deal_impression` — `{deal_id, source, position}`.

In the console (`flutter run`):

```
[rescu HH:MM:SS.mmm] analytics: deal_impression {deal_id: 7, source: home, position: 0}
[rescu HH:MM:SS.mmm] POST /analytics/batch events=1
```

The batch flush POST fires 15s after the first unsent event, or immediately
on the 10th.

## Test plan

- [x] `fvm flutter analyze` — **clean**.
- [x] `fvm flutter test` — **53 passing** (up from 41; +12 for F-2).

### Tracker (`test/impression_tracker_test.dart`, 8 tests)

- Session dedup: same deal id across `home` / `search` / `flash_rail` records
  once. Different deal ids record independently.
- Batch flush triggers:
  - 10 events → immediate flush (asserts `sendAnalyticsBatch` received a 10-item list).
  - Fewer than 10 → flush after 15s (`fakeAsync` drives the timer).
  - **15s clock anchored on the FIRST unsent event, not the last** — an
    event added at t=10s does NOT reset the flush timer; flush still fires
    at t=15s carrying both events.
  - Post-flush, the next event starts a fresh 15s window.
- Robustness: a backend `sendAnalyticsBatch` failure doesn't crash the
  tracker and doesn't strand pending events. `flush()` with an empty batch
  is a no-op.

### Widget (`test/impression_tracked_widget_test.dart`, 4 tests)

- **Does NOT fire before 1 continuous second** — 500ms of visibility
  doesn't log.
- **Fires after 1 continuous second** — asserts the exact
  `{deal_id, source, position}` on the emitted event.
- **Scrolling past in <1s must not fire** — the trap. Widget is visible for
  400ms, then removed from the tree; 5 more seconds elapse; nothing
  records.
- **Same deal on two surfaces logs once, not twice** — session dedup on
  the tracker side is what enforces this.

Both widget tests explicitly cancel `tracker.onClose()` at end of body —
the tracker's 15s flush timer is a real pending timer that flutter_test
correctly flags. Same class of assertion as the RES-102 lifecycle test.

## Performance considerations

The trap says "scrolling performance must not regress". Two costs to reason
about:

1. **`VisibilityDetector` overhead per wrapped widget.** One extra
   `RenderObject` in the tree per card. The package coalesces visibility
   notifications to ~500ms, so callbacks fire on stabilised state changes
   rather than every scroll frame. On a 20-card viewport this is 20
   `RenderVisibilityDetector`s and, per second of scrolling, a handful of
   callbacks total.
2. **`ImpressionTracker` per-call cost.** `Set.contains` + `Set.add` +
   `List.add` — O(1). The dedup short-circuit means once a deal is logged,
   every subsequent widget's callback for that deal is a single `Set.contains`
   check and return.

Not doing:

- **Reference-counting the ticker** the way F-1's `CountdownTicker`
  arguably could. `VisibilityDetector` doesn't have a shared ticker — it's
  event-driven off Flutter's layout pipeline.
- **Persisting `_seen` across app restarts.** The ticket says "per
  session"; a fresh launch is a fresh session.

## Deliberate omissions

- **`deal_impression` on details / cart / map.** Reasoned above.
- **Sending `screen`, `user_id`, or timing metadata on the batch.** Not in
  the ticket's spec (`deal_id, source, position`), and `sendAnalyticsBatch`
  is a fake stub anyway. Would round-trip if the real backend required them.
- **Retry on failed batch flush.** Silent drop is defensible: the local
  sink still has the events for debugging, and impressions are best-effort
  telemetry — losing one on a network blip isn't a product-breaking
  outcome. A retry queue could be added if the tracker moved into a real
  analytics pipeline.
- **Per-tracker configurability** of `maxBatchSize` / `maxBatchAge`.
  Currently constants matching the ticket's spec. Making them constructor
  args would help downstream A/B tests; not needed for this task.
