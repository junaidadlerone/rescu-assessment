# F-3 — Stock reservations with optimistic UI

## What shipped

Adding a deal to the bag now reserves stock for 5 minutes via
`POST /reservations`. The item appears in the bag **before** the network
round-trip lands (optimistic UI) and the outcome is reconciled after:
success attaches the reservation, 409 rolls the line back with a
customer-friendly message. Each cart line displays its remaining hold
(mm:ss), removing a line releases its hold, and checkout passes
reservation ids and survives a 410 without corrupting state.

## The product decision — what happens when a hold lapses

The ticket calls this out as deliberately unspecified. Two moments matter,
and I chose different behaviours for each on purpose:

### On browse — passive: mark the line as expired, show a Refresh button

**Chosen.** The user sees a line whose hold has expired render with a
"Hold expired" tag and a Refresh action. Tapping Refresh attempts a new
`reserveDeal` for the same quantity. Success replaces the reservation
and releases the old one; failure surfaces "Still no luck — that deal
sold out" and leaves the line in place so the user can decide to remove
it themselves.

**Rejected: auto-remove with a snackbar** (the flash-sale expiry pattern
from F-1). The bag represents user intent — someone left their phone on
for six minutes and came back to see three items silently vanish is a
worse experience than a clear "hold expired, tap to refresh" affordance.
The framing that resolved this: flash-sale expiry is the **supplier**
withdrawing the deal ("we're closed"), which is permanent — remove.
Reservation expiry is **my grip lapsing** ("your five minutes are up"),
which may or may not be permanent — the underlying stock could still be
there. Different semantics, different UX.

### On checkout — surface early, don't paper over

**Chosen.** Before posting `POST /checkout`, the CartController does a
local check: any line whose reservation is locally expired blocks the
call and prompts the user to refresh the affected lines. If the local
check passes but the server still returns 410 (clock skew, or the
round-trip crossed the expiry boundary), the same UX fires — a snackbar
with the specific instruction, no crash, no partial charge.

**Rejected: automatic re-reserve + silent retry at checkout time.**
Papering over a 410 with an invisible re-reserve hides real stock
contention. If Rescu's reservations start rejecting because deals are
selling out, we want the user to see it and choose again — not paper
over it and risk them thinking the order confirmed when it didn't.

## Optimistic add flow

```
User taps Add
  → CartService.add() runs synchronously to insertion:
       items.add(placeholder)     — line visible in bag immediately
       reservingDealIds.add(id)   — UI shows "Reserving..." spinner
       itemCount.value++
  → await orderRepo.reserve(dealId)   [~350-1100ms]
     ↳ success:
         line.reservation = <hold>
         analytics: reservation_created
     ↳ 409 (~1 in 5, deliberate):
         items.remove(placeholder)
         itemCount.value--
         snackbar: "Someone grabbed the last one — try another?"
         analytics: reservation_failed
     ↳ finally: reservingDealIds.remove(id)
```

**Edge case — user removes the optimistic line before reserve returns.**
`CartService.add` checks whether the line still exists after the await
returns. If not, the reservation is an orphan; it gets released
immediately with `releaseReservation`. Regression witness in
`test/cart_reservation_test.dart` — "user removes optimistic line before
reserve returns — orphan hold released".

## Per-line countdown

Each cart line renders one of three states via a single `Obx` scoped to
the status row (never the whole card). The Obx reads
`CountdownTicker.now.value`, so it ticks at 1Hz just like F-1's
`FlashCountdown`:

- **Reserving** — spinner + "Reserving stock…"
- **Active** — 🔒 "Held for `mm:ss`"
- **Expired** — ⚠ "Hold expired" + Refresh button

No new timer per line. Reuses F-1's `CountdownTicker` service — one
timer for the whole app.

## Checkout resilience

`CartController.checkout` now does:

1. Empty-bag / already-checking-out guard (unchanged).
2. **Proactive expired-hold check.** Local scan; if any line's reservation
   is expired, block and snackbar with count. No POST fires.
3. `orderRepo.checkout(items)` with all reservation ids.
4. On success: `cart.clearAfterCheckout()` (does NOT release — server
   already consumed the holds), snackbar with order id.
5. On `ApiException.statusCode == 410`: same snackbar as (2) — "hold
   expired mid-checkout, tap refresh on affected lines".
6. On any other ApiException: unchanged behaviour ("Checkout failed" with
   API message).

The distinction between (2) and (5) matters for analytics: both fire, but
under different event names (`checkout_blocked_expired_holds` vs
`checkout_rejected_stale_hold`). If (5) starts firing often, we know
there's a clock-skew or expiry-boundary issue to investigate; if only (2)
fires, users are just leaving the app open.

## Analytics events

Visible on **Home → ⋮ → Analytics debug**:

- `reservation_created` — `{deal_id, reservation_id}` on successful add.
- `reservation_failed` — `{deal_id, status}` on rollback.
- `reservation_refreshed` — `{deal_id, reservation_id}` on successful Refresh.
- `reservation_refresh_failed` — `{deal_id, status}`.
- `checkout_blocked_expired_holds` — `{expired_count}` (proactive block).
- `checkout_rejected_stale_hold` — `{status}` (server-observed 410).
- `checkout_success` — `{order_id}`.
- `checkout_failed` — `{status}` (non-410).

### `test/cart_reservation_test.dart` (11 tests)

- **Optimistic add**:
  - Line appears BEFORE reserve returns, marked as reserving; success
    attaches the reservation.
  - 409 rolls back the optimistic insert; itemCount goes to 0.
  - User removes the optimistic line before reserve returns — orphan
    hold released.
- **Removals release the hold**:
  - `remove()` releases the reservation.
  - `decrement` to zero releases.
  - `clear()` releases all.
  - `clearAfterCheckout()` does NOT release (server consumed them).
- **Expiry / refresh**:
  - `isReservationExpired` flips true past TTL.
  - `holdRemaining` decrements on tick.
  - `refreshHold` replaces the reservation on success and releases the
    old one.
  - `refreshHold` failure keeps the expired line in the bag for another
    try — does not silently remove.

The `_FakeOrderRepo` uses `Completer<ReservationModel>`s keyed by dealId
so tests control resolution order (same shape as the fake repos in
`home_controller_race_test.dart` and `deal_details_controller_test.dart`).
Its `expiresAt` anchors to the injected `CountdownTicker`'s "now" so
TTL assertions aren't wall-clock-dependent — a subtle bit that caught me
on the first run (initial fake used `DateTime.now()` while the ticker
was set to 2026, so `holdRemaining` was returning ~8 months).

## Deliberate omissions

- **Per-quantity reconciliation.** Incrementing a line locally does NOT
  currently re-reserve at the new quantity. First successful reserve
  sets `reservation.quantity`; local increments diverge. In production
  this would either (a) re-reserve on every increment and release the
  old, or (b) treat each unit as its own reservation. Scope-appropriate
  simplification for the fake API's shape; the checkout endpoint would
  reject if `sum(reservation.quantity) < line.quantity`, so the bad case
  surfaces as a checkout-time failure rather than a silent overcount.
- **Retry on transient release failure.** `DELETE /reservations/:id`
  failures are logged but not retried. Reservations expire server-side
  in 5 minutes anyway; failing to release just holds stock a little
  longer than needed.
- **Warning UI as a hold approaches expiry.** No amber-flash on the last
  30 seconds. Nice-to-have polish, not the ticket's core.
- **Persisting reservations across app restart.** Fresh launch = empty
  bag = no cached holds. If the app comes back, the reservations
  server-side keep ticking; without a "restore session" mechanism we
  can't reclaim them. Out of scope.
