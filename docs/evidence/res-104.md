# RES-104 — before/after

## Repro (deterministic)

`test/home_controller_race_test.dart` — 4 tests, uses a `_FakeDealRepo` whose
`fetchDeals` returns `Completer` futures the test resolves in a chosen order.
No wall-clock timing, no flakiness.

Two of the four tests fail on the pre-fix `home_controller.dart` with clear
diagnostics that map directly onto the two symptoms in the ticket:

```
✗ refresh during in-flight loadMore drops the stale page-2 (page-1 wins first)
    Expected: <20>
    Actual:   <40>            ← the "cards duplicate" symptom

✗ two rapid refreshes: stale older result loses when it lands late
    Expected: <15>
    Actual:   <20>            ← the "feed reverts to stale data" symptom
```

All four pass on the fix.

## Manual repro (for completeness)

On the Pixel 4 emulator in debug mode: cold-start, fast-scroll to bottom to
trigger `loadMore`, immediately fling back to the top and pull-to-refresh
before page 2's response lands (`_latency(min: 250, max: 950)` gives ~600ms
of window). Watch `flutter run`'s log for overlapping `GET /deals?page=2`
and `GET /deals?page=1`. On-screen, a duplicated card or a card count that
goes 20 → 40 → 20 is the confirmation.

The unit tests exist because this manual repro is inherently timing-dependent
and can't be part of CI.

## Root cause

Two async operations mutate the same `deals` list without coordinating:

- `refreshDeals()` calls `deals.assignAll(page1)` — wipes and replaces.
- `loadMore()` optimistically bumps `_page++`, then calls `deals.addAll(page2)`
  — appends.

If a refresh starts while a `loadMore` is in flight, the two responses race
on `deals`. Neither call knows about the other. `_isFetchingMore` gates
concurrent `loadMore`s but does nothing to coordinate with `refreshDeals`.

Two interleavings, both broken:

- **Refresh lands first, then stale loadMore.** `assignAll(page1)` replaces
  the list, then `addAll(page2)` appends stale data. Result: fresh page 1
  + stale page 2 on screen, and `_page` reset to 1 by refresh — so the next
  scroll-to-bottom fetches page 2 *again* → duplicate cards.
- **Stale loadMore lands first, then refresh.** `addAll(page2)` appends onto
  the old page 1 (40 items visible), then `assignAll(page1_fresh)` replaces
  the whole list with 20 items. User sees the feed briefly grow, then snap
  back — and page 2 was silently lost.

`_page++` before the await is a related latent bug: on error the `_page--`
recovers, but on a refresh race it drifts from what's actually in `deals`.

## Fix

Monotonic epoch counter — the same pattern that will apply to RES-101's
search race:

- `_refreshEpoch` bumps synchronously at the start of every `refreshDeals()`.
- Both `refreshDeals` and `loadMore` capture the epoch when they start and
  check it before mutating `deals`. Response with a stale epoch is dropped.
- `refreshDeals` on success resets `_isFetchingMore = false` so any
  post-refresh `loadMore` can start fresh, and calls `loadComplete()` so the
  pull-to-refresh footer doesn't get stuck if a `loadMore` was in flight.
- `loadMore` no longer touches `_page` optimistically. Target page is
  computed locally; `_page` is only assigned on a successful, non-stale
  response. Removes the "increment then decrement on error" fragility.
- Both methods wrap in `try/finally`. The original `refreshDeals` called
  `refreshCompleted()` *after* the `await`, not in a `finally` — meaning a
  thrown fetch would leave the pull-to-refresh spinner spinning forever.
  Fixed as a bonus.

## Rejected alternatives

- **Dedup `deals` by id after every mutation.** Hides duplicate cards but
  leaves `_page` drifting from actual list contents, and doesn't help the
  "feed shrinks" ordering. Explicitly rejected — this is the "hide the
  symptom" trap the ticket warns about.
- **Single mutex over `refreshDeals` and `loadMore`.** Would prevent the
  race by serializing all fetches, but pull-to-refresh would then feel
  frozen whenever a `loadMore` was in flight. Rejected for UX. The epoch
  approach lets both fire concurrently and just ensures they can't corrupt
  each other's state.
