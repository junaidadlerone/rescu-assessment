# RES-105 — after

Compared to `docs/evidence/res-105-baseline.md`. Same device (Pixel 4 AVD,
Android 11, density 440 → dpr ~2.75), same build mode (profile), same
`fvm flutter run --profile -d emulator-5554`.

## Fixes shipped

Each of the four causes named in the ticket is addressed independently.

### 1. `Obx` scope — home screen no longer rebuilds per scroll frame

The outer `Obx` in `home_screen.dart` wrapped the whole `Scaffold` and read
`scrollOffset.value`, which changes on every scroll frame. That triggered a
full-screen rebuild at ~60Hz while scrolling.

Fix: removed the outer `Obx`. Split into three targeted islands:

- `_HomeAppBar` extracted, its own `Obx` reads only `showAppBarShadow.value`.
- Body `Obx` reads `isLoading`, `flashDeals`, `todayOnly`, and `visibleDeals`.
- FAB `Obx` reads only `showScrollToTop.value`.

`scrollOffset.value` is gone entirely. Replaced with two threshold-crossing
booleans (`showAppBarShadow`, `showScrollToTop`) that only flip when the user
crosses the visual thresholds — a scroll from 0 to 900 flips each exactly
once, not 60 times per second. Setter is guarded (`if (current != next)`) so
we don't emit spurious `RxBool` notifications.

### 2. Lazy list — `ListView(children:)` → `CustomScrollView` + `SliverList.builder`

Original body was `ListView(children: [flashSection, header, ...allCards, spacer])`.
`ListView`'s default constructor materialises every child up-front and never
recycles them. All 122 `DealCard` widgets existed in memory simultaneously.

Fix: `CustomScrollView` with three sliver kinds:

- `SliverToBoxAdapter` for the flash rail and the "Nearby deals" header.
- `SliverList.builder(itemCount, itemBuilder)` for the cards — Flutter now
  builds only cards inside the viewport ± cache extent, and reuses their
  `Element`s as items scroll off.
- `SliverToBoxAdapter` for the trailing 24px spacer.

### 3. Image decode size — `memCacheWidth` / `memCacheHeight` on `TheNetworkImage`

Source images from `picsum.photos/.../1600/1200` were being decoded at
`1600 × 1200 × 4 bytes = ~7.7 MB` per image regardless of the box they
painted into. Cards paint into a 160px-tall box; the flash rail paints
into a 90px-tall box. Both were paying the full source cost.

Fix: `TheNetworkImage` now computes `memCacheWidth`/`memCacheHeight` from
its `width`/`height` scaled by `MediaQuery.devicePixelRatioOf(context)`.
Callers can override; the defaults are correct for the two lists.

On this Pixel 4 (dpr = 2.75):

- Card image: `160 × 2.75 ≈ 440` px tall → decoded ≈ `587 × 440 × 4 ≈ 1.0 MB`.
  ~7.5× smaller than before.
- Flash rail image: `90 × 2.75 ≈ 248` px tall → decoded ≈ `330 × 248 × 4 ≈ 0.33 MB`.
  ~23× smaller than before.

Both branches of `TheNetworkImage` (main image + placeholder) already had
`width`/`height`; only the `CachedNetworkImage` needed the cache hints.

### 4. `visibleDeals` — no allocation on read

Was `List<DealModel> get visibleDeals => ... .toList()` — allocated a fresh
list on every read. Because of cause 1, "every read" meant "every scroll
frame".

Fix: return type changed to `Iterable<DealModel>` and the `.toList()` copies
dropped. The `else` branch now returns the `RxList` itself (which *is* a
`List<DealModel>`). The filtered branch returns a lazy `.where(...)`
iterator. `home_screen.dart` materialises it exactly once per rebuild with
`.toList(growable: false)` for the sliver's `itemCount`/`itemBuilder`.

Even before that change, cause 1's fix drops the read frequency from
60Hz to "when `deals` or `todayOnly` actually change", so this is now a
minor optimization on top of a much rarer path.

## Measurements

### Memory (PSS, via `dumpsys meminfo dev.rescu.rescu`)

|                                | Before          | After           |
|---                             |---              |---              |
| Cold, on home                  | 113.9 MB        | 117.1 MB        |
| After ~10–30 fast swipes       | 130.6 MB        | 120.5 MB        |
| Peak during heavy interaction  | 133.5 MB        | 136.3 MB        |

The overall PSS envelope is similar because the catalog is bounded (122 deals)
and Flutter's default 100MB `ImageCache` was already evicting on both sides.
The real memory win happens where a bounded fixture can't show it — image
cache turnover is 7–23× cheaper per decode, so on a larger catalog or a
tighter memory budget the fixed build stays comfortably under the heap
growth limit where the buggy one would evict-and-redecode continuously.

### Frame timing (attempted)

Baseline captured 129 frame timestamps via
`dumpsys SurfaceFlinger --latency 'SurfaceView - dev.rescu.rescu/.../MainActivity#0'`.
The **same command** on this session's emulator returns 1 line (only the vsync
period, no per-frame records) for that layer, and all-zero records for
`Root#0`. `dumpsys gfxinfo` returns `Total frames rendered: 0` because Flutter
paints via its own `FlutterSurfaceView` and bypasses HWUI — noted in the
baseline doc too.

Attempts made and outcomes:

- `SurfaceFlinger --latency-clear` → `--latency` on `SurfaceView - ...`: 1
  line, no frame records. Baseline used the identical command.
- Same on `Root#0`: 129 lines but all-zero timestamps.
- `dumpsys gfxinfo dev.rescu.rescu framestats`: `Total frames rendered: 0`.
- Fresh cold-restart + immediate capture: same result.

Not repeated: attaching to the VM Service programmatically to pull
`FrameTiming` events (requires a small script; scope creep on a bug-fix PR),
or adding an in-app `SchedulerBinding.addTimingsCallback` (requires
instrumentation that has to be reverted before commit).

For the "after" evidence I fell back to:

- Screen recording (`/tmp/rescu-after/scroll-after.mp4`, 15s of continuous
  scroll — smooth, no visible stutter). Not committed, too large; can be
  re-recorded on the fixed build with `adb shell screenrecord`.
- Screenshot of the settled home feed after ~30 swipes:
  `docs/evidence/res-105-home-after.png`.
- Console log from `flutter run --profile`: **zero exceptions, zero
  "frame skipped" warnings** across the ~90-swipe session used to capture
  memory. On the baseline these were routine.

## What's not fixed here — deliberate scope

- `deal_details_screen.dart` also calls `TheNetworkImage` without `width`/
  `height`, so the details hero image is still decoded at source size.
  Out of scope: ticket names three files, this is not one of them, and a
  single hero image on a detail screen is not the ballooning-cache problem.
- The Pickup Window still displays UTC times on the "after" screenshot
  (`13:00 – 16:00` in the second card — market is Bangkok, my emulator is
  Karachi). That is RES-106, tracked separately.
