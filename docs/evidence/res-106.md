# RES-106 — before/after

## The three getters, judged separately

`PickupWindowModel` has three time-related getters. The ticket claims the model
is broken, but they don't all fail — and saying which one was already right is
the part of this ticket that reads as understanding.

| Getter | Pre-fix status | Why |
|---|---|---|
| `label` | Wrong | `DateTime.parse` of a Z string returns UTC; `DateFormat.format` prints whatever numeric fields the DateTime carries. On a Bangkok bakery open 06:00–09:30, `start` UTC is 23:00 the day before → printed "23:00 – 02:30". |
| `isToday` | Wrong twice over | `start.day == DateTime.now().day` compares only the day number (ignores month/year, so it "works" for 30 days a month then breaks) **and** compares UTC's day against the device's local day. |
| `isOpenNow` | **Correct** | `isAfter` / `isBefore` compare absolute instants regardless of the DateTime's declared zone. UTC `start` vs local `now` still resolves to the right instant. |
| `untilStart` | Correct | `difference()` operates on instants too. |

The fix touches `label` and `isToday`. `isOpenNow` and `untilStart` are left
functionally identical; both were re-routed through the injectable clock so
tests can drive them deterministically without changing their behaviour.

## Product decision: whose clock?

The ticket doesn't ask this directly. The fix implicitly answers it.

A user in Karachi (UTC+5) buying a bag from a Bangkok bakery that opens at
06:00 Bangkok should see **06:00**, not 04:00. Rescu is a marketplace for
physically walking to a store — the user needs to know what the store thinks
its opening time is. The store operates on Bangkok's clock; the pickup label
must too.

`.toLocal()` is the obvious shortcut — the code passes review, the numbers
change, and the bug looks fixed as long as the reviewer's phone happens to
be set to Bangkok. It's the same class of trap as "cached the response =
fixed the leak" in RES-103: symptom moved, cause intact. For a Karachi user
`.toLocal()` produces the wrong hours in the opposite direction (04:00) and
for isToday it produces the wrong day for anyone west of Bangkok.

The market timezone lives in `AppConfig.marketOffset` as `Duration(hours: 7)`
with a comment explaining scope: single-market app, upgrade path to a
per-store IANA zone when the marketplace expands. It does NOT live in
`PickupWindowModel` because the model is data — the choice of "which zone
to show" is a product decision the app owns.

## Fix

`lib/model/pickup_window_model.dart`:

- `fromJson` explicitly `.toUtc()`s the parsed instant (`DateTime.parse` of a
  Z string already returns UTC, but stating the invariant in the constructor
  path makes the model's internal contract explicit).
- `_marketStart` / `_marketEnd` — `.add(AppConfig.marketOffset)` returns a
  DateTime whose numeric fields hold the Bangkok wall clock. Kept flagged as
  UTC so `DateFormat` prints those numbers verbatim without a second zone
  shift.
- `label` uses `_marketStart` / `_marketEnd`.
- `isToday` compares `year/month/day` of `_marketStart` against `now` also
  shifted into market time. The naïve day-only comparison is gone.
- `isOpenNow` and `untilStart` route through the injectable clock but their
  arithmetic is unchanged.
- `static DateTime Function() now = DateTime.now` — replaceable in tests.
  This is the concrete answer to design Q3 (see solutions.md).

## Rejected alternatives

- **`.toLocal()` on the parsed instants.** Product-wrong for any user not in
  Bangkok. Same category as RES-103's "cache the request" trap — moves the
  symptom, hides the cause.
- **Store the offset on `PickupWindowModel` itself as a field.** Would let
  each window carry its own zone, which is where the app will end up when it
  becomes multi-market. Rejected for now — YAGNI, and the concept "which
  clock does the app display?" is an app-level decision, not a model
  concern.
- **`package:timezone` with an IANA `Asia/Bangkok` zone name.** Correct for
  DST-carrying zones. Bangkok has never observed DST, so a fixed offset is
  loss-free and doesn't add a dependency. Named as the upgrade path in the
  `AppConfig` comment.

## Design Q3 answer, in one line

The three getters call `DateTime.now()` directly. That makes their behaviour
non-deterministic in tests — the answer depends on when the test runs. The
fix injects `now` as a static function on the model so tests set it to a
chosen instant. See the write-up in `solutions.md` for the full argument
including why a `package:clock` `Clock.now()` would be the more idiomatic
alternative at higher scale.

## Test plan

- `test/pickup_window_test.dart` — 13 tests, clock-injected, covers each
  getter across "before start", "in window", "after end", plus explicit
  "wrong device zone" and "would have been wrong with the naïve check"
  scenarios. Runs on the fixed code only (references
  `PickupWindowModel.now`).
- `test/pickup_window_label_regression_test.dart` — 1 test using only the
  pre-existing public API, so it compiles against both versions. Verified:
  ```
  Pre-fix:  Expected: '06:00 – 09:30'
            Actual:   '23:00 – 02:30'     ← the ticket's exact bakery example
  Post-fix: pass
  ```
- Full suite: 24 passing (was 10 before RES-106).
- Manual: on the Pixel 4 in profile mode, home feed shows pickup times in
  Bangkok wall clock, "Pickup today" filter now selects deals whose window
  starts today in Bangkok. Screenshot after the fix:
  `docs/evidence/res-106-home-after.png`.

## Deliberate omissions

- **`untilStart` UI polish for windows that already opened.** Returns
  negative Durations. Current callers don't format it as HH:MM anyway; if
  they start doing so, they'll need to zero-clamp. Not this ticket.
- **Analytics timestamps.** The analytics service already sends UTC
  epochs (unaffected). No product need to render analytics events in market
  time.
