# RES-107 — before/after

## The bug in one line

`deal = Get.arguments as DealModel;` — a hard cast that a deep link (which
carries no `arguments`, only query params) can never satisfy.

## Why the same URL worked from the feed

The screen has two entry paths and they pass data differently:

| Entry | `Get.arguments` | `Get.parameters['id']` |
|---|---|---|
| Feed card / flash rail tap | The whole `DealModel` | id string (from URL) |
| Deep link (`rescu://open/deal?id=42&source=push`) | `null` | id string |

The pre-fix controller assumed feed-style. On a deep link the cast blew up
with the exact error the ticket names:

```
type 'Null' is not a subtype of type 'DealModel'
```

Regression witness at `test/deal_details_deep_link_regression_test.dart`
reproduces that error verbatim on the pre-fix code and passes on the fixed
code.

## Fix, in three parts

### 1. Controller accepts either shape

- If `arguments` is a `DealModel`, adopt it synchronously — no network call.
  The feed / flash-rail flow keeps its zero-latency behaviour.
- If not, parse `id` from `parameters['id']` and fetch. Loading state is
  visible on the screen while the fetch is in flight.
- If both are absent or the id doesn't parse, land in an explicit error
  state with a Retry button (the "malformed link" case). Rare but real —
  a mis-typed link is different from a valid id whose fetch happened to
  fail, and only the latter benefits from Retry.

### 2. `deal` becomes reactive

Was `late final DealModel deal;` — set once at construction, non-null,
read directly in `build()`. Any late-arriving data would blow up on the
`late final` re-assignment.

Now `Rxn<DealModel>`, exposed via `DealModel? get deal`. The screen wraps
its top-level branching in one `Obx` that resolves to one of three
scaffolds:

- `_LoadedScaffold` — the original UI, unchanged.
- `_LoadingScaffold` — small AppBar, centered spinner. Shown for the ~250–950ms
  the fake API takes to answer.
- `_ErrorScaffold` — message + Retry button.

### 3. `addToCart` and `_recheckAvailability` guard on nullability

- `addToCart` early-returns when `deal` is null (belt-and-braces: the button
  itself is disabled via `controller.canAddToCart` while loading / on error).
- `_recheckAvailability` early-returns if the deal isn't loaded yet — the
  `ever(cartService.itemCount, ...)` `Worker` is wired up **after** the
  deal is adopted, but even if a cart change slips in between (nothing in
  the current app does that), the callback is safe.

## Rejected alternatives

- **Null-check with a "Deal not found" screen for every deep link.** What
  the ticket explicitly rules out — deal 42 exists in the API, the link
  should work. Would trade a crash for a lie.
- **Repository-level cache to make `fetchById` cheap enough that fast path
  vs slow path stops mattering.** Solves a different problem (network cost)
  while leaving the crash intact. And a hot cache would hide latency
  variance the screen still needs to handle correctly.
- **Passing the deal id as a route path segment (`/deal/42`) instead of a
  query param.** Cleaner URL shape, but the ticket says "keep deep link
  as is" and the in-app callers already use `Routes.dealRoute(id, source:)`
  which builds the query-param form. Not worth the churn on this ticket.

## Testing seam and why it exists

`Get.arguments` and `Get.parameters` are getter-only on the GetX facade —
they read from the current navigator's route settings. In a unit test
there is no navigator, and the facade offers no way to inject test values.

The controller now takes two optional readers:

```dart
DealDetailsController({
  ...
  Object? Function()? argumentsReader,
  Map<String, String?> Function()? parametersReader,
})
```

Defaults are `() => Get.arguments` and `() => Get.parameters`, so the
binding and the production code path are unchanged. Tests supply stubs
that return whatever the scenario requires. This is a testing seam that
also happens to make the controller more honest about what it depends on
— the router surface is now visible in the constructor.

## Deliberate omissions

- **Router-level validation of `id`.** Would be cleaner than the controller
  parsing the string. Out of scope for this ticket; the controller-level
  guard is the minimum sufficient fix.
- **A skeleton loader that mirrors the loaded layout.** Nicer UX than a
  centered spinner, especially since we know the shape the layout will
  take. Cost: another widget to keep in sync with `_LoadedScaffold`. Not
  what this ticket is asking for.
